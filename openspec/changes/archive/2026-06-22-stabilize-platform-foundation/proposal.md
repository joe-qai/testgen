## Why

TestGen 当前的 API 异常响应、核心查询索引和运行状态检查缺少统一基线，导致故障信息可能直接暴露、数据增长后查询退化，并且服务异常难以及时定位。现在需要优先补齐这三项彼此关联的稳定性能力，为后续性能与监控建设建立可验证的基础。

## What Changes

- 建立统一的 API 错误响应契约，区分客户端错误、资源不存在和服务端异常，并为未处理异常提供集中日志记录。
- 保留端点已有的业务状态码与信息，同时确保服务端异常不向客户端泄露内部异常文本。
- 为需求、测试用例和生成任务的高频过滤、关联与排序字段增加数据库索引，并提供可重复执行的迁移路径。
- 提供基础运行状态接口，分别呈现应用存活状态和数据库可用状态。
- 增加覆盖成功、边界、失败与旧数据库升级场景的自动化测试。
- 三项能力保持在一个 change 中统一设计和回归验证，因为它们共同构成平台稳定性基线；任一项单独交付都无法完成本轮整体稳定性验收。

## Capabilities

### New Capabilities

- `api-error-contract`: 规定 API 错误的统一结构、状态码保留、异常信息保护和服务端日志行为。
- `database-query-indexing`: 规定核心业务查询所需索引以及新旧数据库的一致、安全初始化行为。
- `operational-health`: 规定应用存活和数据库就绪状态的基础检查接口及降级响应。

### Modified Capabilities

无。

## Impact

- 主要影响 `app.py`、`src/api/routes.py`、`src/database/models.py`、数据库迁移目录和对应测试。
- API 的成功响应与业务流程保持不变；错误响应将形成稳定契约，现有依赖内部异常字符串的调用方需要改用标准字段。
- SQLite 仍是本轮数据库方案，不引入 PostgreSQL、Redis、Celery、Prometheus 或 Grafana。
- 不包含前端框架重构、微服务拆分、业务生成逻辑修改或完整可观测平台建设。
