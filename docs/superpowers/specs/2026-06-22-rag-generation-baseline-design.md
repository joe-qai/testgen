# RAG 生成基线稳定化技术设计

## 目标与边界

本次变更恢复 Phase 2 已在技术方案中定义但当前实现缺失的两层召回：需求级全局召回执行一次，每个 ITEM 在生成前执行一次精准召回，二者合并后传给对应 ITEM 的生成调用。同时修复全局缺陷上下文的重复拼接。

实现保持在 `GenerationService` 内，不拆分服务，不修改 REST API、数据库结构、WebSocket 事件、前端交互或底层检索算法，也不处理本次基线之外的空测试。

## 测试审查门禁

生产代码修改前，逐条审查当前 9 个失败测试，并记录以下结论之一：

- 测试错误：mock 返回形态、调用假设、隔离方式或断言与公开契约冲突，先修复测试。
- 测试陈旧：断言已不属于确认后的需求，修改或移除陈旧预期。
- 实现缺陷：测试可映射到 delta spec 的明确场景，保留为红灯测试并驱动最小实现。

测试失败本身不构成修改生产代码的理由。只有逻辑正确、契约明确且隔离可靠的测试可以驱动实现。

## 运行时数据流

```text
需求内容
  -> 全局 RAG 召回（每个 Phase 2 任务一次）
  -> 遍历 ITEM
       -> ITEM 标题 + 测试点构造局部查询
       -> ITEM 精准召回与有限降级
       -> 局部优先合并全局上下文并精确去重
       -> generate_item_cases(merged_rag_context)
```

全局召回继续提供需求、跨模块用例和历史缺陷背景。ITEM 召回负责提高当前测试项的局部相关性。局部召回异常时，该 ITEM 回退使用全局上下文，生成主流程不中断。

## 组件与方法契约

### ITEM 查询构造

新增或恢复 `GenerationService._perform_item_rag_recall(item_title, item_points, top_k=5) -> Dict[str, Any]`。原始查询由非空 ITEM 标题和规范化后的测试点标题按稳定顺序连接；没有测试点时只使用 ITEM 标题。

`QueryOptimizer` 仅作为可选增强。关键字提取成功时用于丰富查询，初始化失败、返回空值或抛出异常时直接使用原始查询。当前不接入 `QueryOptimizer.parallel_search`：其返回形态与现有 `HybridRetriever.retrieve` 契约存在差异，接入会把本次基线修复扩展为底层检索器改造。

### 稳定返回结构

ITEM 召回在成功和可恢复失败路径均返回同形字典，至少包含：

- `rag_context: str`：可直接注入生成提示词的上下文。
- `results: Dict[str, Any]`：按集合保存的原始召回结果。
- `quality_alert: Optional[str]`：如 `no_results`、`low_similarity`。
- `degraded: bool`：是否使用降级结果。
- `stats: Dict[str, Any]`：查询、结果数量和检索次数等可观测信息。

检索器不可用时返回空结果、空上下文、无质量告警和稳定统计信息。可恢复异常被记录并转换为降级结构，不向 Phase 2 主循环抛出。

### 检索与质量降级

ITEM 召回复用现有 `HybridRetriever` 和 `RetrievalEvaluator`，不改变向量检索、关键词检索或 RRF 融合算法。

- 正常结果：格式化为带来源标识的局部上下文。
- `no_results`：设置 `degraded=true`，返回“无历史参考数据”的提示。
- `low_similarity`：使用扩大后的 top-k 最多补充检索一次，并保留质量告警。
- 优化器异常：使用原始查询完成首次检索，不额外消耗重试次数。

补充检索必须有明确上限，避免低质量结果造成递归或无界检索。

### 上下文格式与引用

每条历史结果保留可识别的集合类型、来源标识和正文。存在历史用例时，局部上下文附带包含 `citation` 字样的引用标注要求，使下游生成结果能够表达来源关系。

`_merge_rag_contexts` 在拼接点完成合并：ITEM 局部段落在前，全局段落在后；按规范化后的完整段落文本进行精确去重，保留首次出现项。此处不做语义去重，以避免误删内容相近但业务含义不同的记录。

全局 `_perform_rag_recall` 中重复的缺陷格式化分支删除，使单条唯一缺陷内容只写入一次。

## Phase 2 集成

需求级 `_perform_rag_recall` 仍在 ITEM 循环外调用一次。循环内为当前 ITEM 调用 `_perform_item_rag_recall`，随后把局部与全局上下文交给合并函数，并将合并结果传入该 ITEM 的 `generate_item_cases`。

集成必须保证：

- 每个 ITEM 使用自身标题和测试点构造查询。
- 一个 ITEM 的局部结果不会泄漏到其他 ITEM。
- 局部召回失败只影响当前 ITEM 的增强上下文。
- 全局上下文仍然存在，不被局部结果替代。

## 测试设计

目标测试先形成审查表，再进行红灯—绿灯实现。mock 必须返回真实依赖的字典形态，断言业务参数和输出，不依赖无业务含义的调用序号。

单元测试覆盖：

- 标题与测试点查询构造，以及无测试点场景。
- 优化器成功、空结果和异常回退。
- 检索器不可用、无结果和低相似度单次扩检。
- 稳定返回结构、来源格式与引用提示。
- 局部优先合并、精确去重和全局缺陷不重复。

流程测试覆盖两个或更多 ITEM，验证每个 ITEM 的局部召回参数正确，并且 `generate_item_cases` 实际收到对应的合并上下文。验证顺序为目标 RAG 测试文件、RAG 相关测试集、全量测试集。

若回归测试失败，继续执行测试逻辑审查门禁；先修复错误用例，只有确认属于本次 spec 的实现缺陷才修改生产代码。

## 风险与控制

- 每个 ITEM 增加检索调用会提高延迟：限制默认 top-k，质量扩检最多一次。
- 精确去重无法处理语义近似内容：本次接受该边界，语义去重留待独立变更。
- 私有方法测试可能过度绑定实现：私有方法只验证稳定输入输出，流程测试负责证明真实接入。
- 依赖返回结构可能存在历史差异：测试 fixture 与适配逻辑以当前公开依赖契约为准，不用脆弱的调用顺序掩盖差异。

## 发布与回退

本次无数据迁移和配置迁移。代码与测试可作为一个原子变更发布；若发生回归，回退本次 ITEM 召回、合并接入与对应测试修改即可，不影响已有数据和 API 契约。
